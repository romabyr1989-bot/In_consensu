# Производительность

Документ отвечает на два вопроса: как измеряется соответствие NFR-1 и что показали измерения. Числа
получены нагрузочным smoke-тестом `PerformanceSmokeIT`, который выполняется в обычной сборке
(`./mvnw verify`) и пишет отчёт в `target/performance-report.md`.

## Цели NFR-1 и что подтверждено

| Операция | Цель NFR-1 | Измерено (smoke) | Статус |
|---|---|---|---|
| Проверка каналов одного субъекта | p95 ≤ 50 мс | 19 мс | в пределах цели |
| Карточка клиента | ≤ 200 мс | 25 мс | в пределах цели |
| Массовая проверка 10 000 идентификаторов | ≤ 2 с | 272 мс на 2 000 (≈1,4 с на 10 000) | в пределах цели |
| Регистрация согласия | ≤ 100 мс | покрыта тестами этапа 3, отдельного замера нет | не измерено |
| Импорт | ≥ 5 000 строк/с | тест этапа 3 импортирует 100 000 строк | не измерено как пропускная способность |

**Честная оговорка о масштабе.** Smoke-прогон выполняется на 2 000 субъектов и 4 000 согласий, а NFR-1
задаёт цели для 5 млн субъектов и 30 млн согласий. Прогон ловит отсутствующий индекс и запрос вида N+1 —
то, что деградирует линейно с объёмом, — но не заменяет нагрузочного испытания на проектных данных.
Такое испытание проводится на стенде заказчика после ответа на вопрос 6 (реальные объёмы и SLA); до тех
пор считать цифры NFR-1 подтверждёнными на боевом объёме нельзя.

## Что нашёл smoke-прогон

Первый же прогон показал массовую проверку в 3,4 с на 2 000 идентификаторов — в восемь раз хуже целевого
темпа. Причины оказались не в индексах:

1. Порог «заканчивается через N дней» читался из `operator_settings` **на каждое согласие**: пакет из
   4 000 согласий давал 4 000 лишних запросов. Настройка теперь читается один раз на пакет.
2. Существование субъекта проверялось вызовом `existsById` **на каждый идентификатор**: 2 000 отдельных
   `SELECT`. Проверка заменена одним запросом `where id in (…)`.

После обоих исправлений — 272 мс на 2 000 идентификаторов. Обе ошибки невидимы в функциональных тестах:
результат был правильным, менялось только время.

## Планы выполнения ключевых запросов

Снимаются тем же тестом и попадают в `target/performance-report.md`.

**Согласия субъекта** — индексный доступ, соответствует `consent_subject_type_status_idx`:

```
Bitmap Heap Scan on consent
  Recheck Cond: (subject_id = …)
  Filter: (superseded_by_id IS NULL)
  ->  Bitmap Index Scan on consent_subject_type_status_idx
```

**Поиск по контакту** — индексный доступ по паре «тип + нормализованное значение»:

```
Index Scan using subject_contact_lookup_idx on subject_contact
  Index Cond: ((type = 'PHONE') AND (value_normalized = '+7…'))
```

**Истекающие согласия** — на тестовом объёме планировщик выбирает последовательное сканирование:

```
Seq Scan on consent
  Filter: ((valid_until >= now()) AND (valid_until <= (now() + '30 days')))
```

Это ожидаемо: в таблице несколько тысяч строк, и индекс `consent_valid_until_idx` (частичный, по статусам
`ACTIVE` и `EXPIRING`) планировщику невыгоден. На проектном объёме выбор изменится; проверить это нужно
на стенде с реальными данными — отдельным пунктом приёмочных испытаний.

## Что влияет на цифры в эксплуатации

- **Шифрование контактов** (`cus.crypto.enabled`, NFR-3) добавляет расшифровку на каждое чтение контакта
  и переводит точный поиск на индекс по HMAC. Карточка и каналы не затронуты: они не читают контакты.
- **Размер пакета outbox** (`cus.notifications.batch-size`) определяет, сколько событий уходит за один
  проход обработчика; при большом числе подписок его имеет смысл уменьшать, чтобы транзакция была короче.
- **Пул соединений** (`INCONSENSU_DB_POOL_SIZE`) по умолчанию 10. Массовая проверка и импорт — операции с
  длинными транзакциями; при их параллельном запуске пул нужно расширять вместе с `max_connections` базы.
- **Ретенция** (NFR-5) переносит отозванные согласия в архивные таблицы и уменьшает рабочие выборки; на
  проектных объёмах это основной способ удержать план запросов индексным.

## Как повторить измерение

```bash
./mvnw verify -Dit.test=PerformanceSmokeIT
cat target/performance-report.md
```

Прогон поднимает PostgreSQL в Testcontainers, наполняет базу вымышленными данными (§14.6) и печатает
измеренные значения вместе с планами выполнения.
