# Webhooks: подписка на события In consensu

Документ для разработчиков систем-потребителей: CRM, колл-центра, маркетинговой платформы. Описывает,
как подписаться на события, как проверить подпись и что делать с повторами.

Требования: FR-9.3, FR-9.4, FR-9.5, §7.9.

## Как это работает

1. Любое изменение согласия записывается в таблицу `outbox_event` **в той же транзакции**, что и само
   изменение (§8.6). Событие не может «уйти» по откатившейся операции и не может потеряться после успешной.
2. Фоновая задача раз в 30 секунд забирает готовые события и рассылает их активным подпискам.
3. Каждая попытка доставки попадает в журнал `webhook_delivery` — с кодом ответа, ошибкой и временем.

Порядок событий по одному согласию сохраняется: пока раннее событие не доставлено, более позднее по тому
же согласию не отправляется. «Отозвано» не может прийти раньше, чем «выдано».

## Подписка

```bash
curl -X POST https://cus.example.ru/api/v1/webhooks \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "name": "CRM",
        "url": "https://crm.example.ru/hooks/cus",
        "eventTypes": ["consent.revoked", "consent.expired"],
        "headers": {"X-Tenant": "retail"}
      }'
```

Ответ содержит секрет подписи. **Он показывается один раз** — при создании и при
`POST /api/v1/webhooks/{id}/rotate-secret`; в списке и карточке подписки его нет.

```json
{
  "subscription": {"id": "…", "name": "CRM", "url": "…", "eventTypes": ["consent.revoked"], "active": true},
  "secret": "0kZ2…"
}
```

Пустой список `eventTypes` означает «все события»: подписка не сломается, когда в In consensu появится новый тип.
Управление подписками доступно ролям ADMIN и INTEGRATION.

## Формат запроса

`POST` на адрес подписки, тело — JSON, заголовки:

| Заголовок | Значение |
|---|---|
| `X-InConsensu-Event` | тип события, например `consent.revoked` |
| `X-InConsensu-Delivery-Id` | идентификатор доставки; **не меняется между повторами** — по нему выполняется дедупликация на стороне потребителя |
| `X-InConsensu-Signature` | `sha256=<hex>` — HMAC-SHA256 тела запроса на секрете подписки |

Плюс произвольные заголовки, заданные в подписке.

```json
{
  "event": "consent.revoked",
  "occurredAt": "2026-08-18T09:12:44.318Z",
  "deliveryId": "5f0a2d1c-4c1e-4a0b-9a9c-7d0a1f3b2e11",
  "consent": {
    "id": "8c2b…",
    "revocationSource": "PERSONAL_ACCOUNT",
    "caseNumber": "ОБР-2026-000431",
    "processingStopDeadline": "2026-09-17T09:12:44.318Z"
  },
  "subject": {"externalId": "CRM-1002345"}
}
```

Персональных данных в теле нет: субъект опознаётся только внешним идентификатором (NFR-3). ФИО, контакты
и категории ПДн получатель берёт из своей системы по `externalId`. Доказательства подписания и отзыва
(телефон, IP, user-agent) остаются в журнале аудита и наружу не уходят — их можно посмотреть в досье
согласия `GET /api/v1/consents/{id}/evidence`.

### Типы событий

| Тип | Когда |
|---|---|
| `consent.granted` | зарегистрировано согласие |
| `consent.revoked` | согласие отозвано; в теле — срок прекращения обработки (30 дней, ч. 5 ст. 21 152-ФЗ) |
| `consent.superseded` | согласие заменено новым того же типа |
| `consent.expiring` | до окончания срока осталось N дней (по правилу уведомления) |
| `consent.expired` | срок действия истёк |
| `form.published` | опубликована новая версия формы |
| `third_party.contract_expiring` | заканчивается договор с третьим лицом |
| `import.finished` | завершён импорт согласий |
| `test.ping` | тестовая отправка `POST /api/v1/webhooks/{id}/test`; обработчик обязан её игнорировать |

## Проверка подписи

Считайте HMAC-SHA256 **сырого тела запроса** (до разбора JSON) на секрете подписки и сравните с
`X-InConsensu-Signature`. Сравнение — константное по времени.

```java
String expected = "sha256=" + HexFormat.of().formatHex(hmacSha256(secret, rawBody));
if (!MessageDigest.isEqual(expected.getBytes(UTF_8), signature.getBytes(UTF_8))) {
    return ResponseEntity.status(401).build();
}
```

```python
import hashlib, hmac
expected = "sha256=" + hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
if not hmac.compare_digest(expected, request.headers["X-InConsensu-Signature"]):
    return Response(status=401)
```

## Ответ и повторы

Успех — любой код 2xx. Всё остальное (включая 3xx), а также таймаут и ошибка сети считаются неудачей.

Расписание повторов: **1 мин → 5 мин → 30 мин → 2 ч → 12 ч**. После исчерпания событие получает статус
`FAILED`, остаётся в базе и не теряется, а администратор получает письмо. Таймауты: 5 с на соединение,
10 с на ответ.

Обработчик обязан быть идемпотентным: одно и то же событие может прийти повторно после сетевого сбоя,
когда In consensu не получил ответ, но получатель его уже обработал. Дедуплицируйте по `X-InConsensu-Delivery-Id`.

Отвечайте быстро: тяжёлую работу выносите в свою очередь, иначе In consensu посчитает доставку неудачной по
таймауту и повторит её.

## Проверка настройки

```bash
curl -X POST https://cus.example.ru/api/v1/webhooks/$ID/test -H "Authorization: Bearer $TOKEN"
curl https://cus.example.ru/api/v1/webhooks/$ID/deliveries -H "Authorization: Bearer $TOKEN"
```

Первый запрос отправляет `test.ping` и возвращает код ответа вашего сервера, второй показывает журнал
попыток. Тестовая отправка не создаёт событие в outbox, но попадает в журнал доставок.

## Что не входит в обязательный объём

Kafka как транспорт (§7.9, вопрос 5 в [`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md)) остаётся опциональным
профилем этапа 8. Список разрешённых адресов подписок (защита от SSRF) — тоже этап 8; до его появления
адреса подписок задают только доверенные роли ADMIN и INTEGRATION.
