## ADR-0001. Версии платформы: Java 21, Spring Boot 3.4, PostgreSQL 16

**Контекст.** §4 фиксирует Java 21 LTS без preview-фич, Spring Boot 3.3+, PostgreSQL 16 и запрет на
обязательные зависимости от зарубежных облачных сервисов.

**Решение.** Spring Boot 3.4.1 (верхняя граница диапазона «3.3+»), Java 21, PostgreSQL 16.
Из версии 3.4 используется встроенное структурированное логирование
(`logging.structured.format.console=logstash`) вместо отдельной библиотеки-энкодера.

**Последствия.** На одну стороннюю зависимость меньше (NFR-6 выполняется средствами фреймворка).
Обновление до 3.5+ потребует проверки совместимости springdoc. Никаких preview-фич Java не
используется, поэтому переход на Axiom JDK или Liberica не требует изменений кода (NFR-4).

## ADR-0002. Модульный монолит, один Maven-модуль

**Контекст.** §4 требует один Maven-модуль, §5 — разбиение на модули по пакетам с правилами
зависимостей.

**Решение.** Один артефакт `ru.example:cus`, границы модулей выражены пакетами
`ru.example.cus.<модуль>.{api,application,domain,infrastructure}`, правила проверяются ArchUnit.
Файлы `package-info.java` зафиксированы для всех десяти модулей сразу, чтобы структура §12
существовала с этапа 0.

**Последствия.** Правила ловятся тестом, а не ревью. Пока модули пусты, ArchUnit-правила
срабатывают вхолостую — поэтому включён `archRule.failOnEmptyShould=false`, который следует
отключить, когда все модули заполнены (этап 7).

## ADR-0003. Корневой пакет `ru.example.cus`

**Контекст.** §5 требует заменить `example` на домен оператора; домен пока не сообщён.

**Решение.** Оставлен `ru.example.cus`. Переименование — механическая операция (одно
переименование пакета и одна правка `groupId`).

**Последствия.** Обратимо. Вопрос вынесен в `OPEN_QUESTIONS.md` (вопрос 10) и должен быть закрыт до
первой поставки в эксплуатацию. Закрыт: решение заменено ADR-0044, пакет — `ru.example.inconsensu`.

## ADR-0004. Baseline-миграция содержит только таблицу ShedLock

**Контекст.** Этап 0 требует «Flyway с baseline», но бизнес-таблицы появляются на этапах 1+.
Пустая миграция не проверяет работоспособность механизма.

**Решение.** `V202608170000__baseline.sql` создаёт таблицу `shedlock` (§4, §6) и фиксирует
соглашения схемы в комментарии: UUID-ключи из приложения, `timestamptz` в UTC, только SQL,
совместимый с Postgres Pro. Расширения PostgreSQL не создаются: `pgcrypto` потребовал бы прав
суперпользователя при развёртывании в контуре заказчика, а SHA-256 считается в приложении (FR-1.6,
FR-10.1).

**Последствия.** Миграции и `ddl-auto=validate` проверяются интеграционным тестом с первого этапа.
ShedLock подключается на этапе 3 без новой миграции.

## ADR-0005. Формат ошибок и корреляция запросов

**Контекст.** §9 требует `ProblemDetail` с `type = urn:inconsensu:error:<code>` и `errors[]`, NFR-3
запрещает ПДн в текстах ошибок, NFR-6 требует request id в логах.

**Решение.** Перечисление `ErrorCode` — единый каталог кодов (код, HTTP-статус, русский заголовок).
`GlobalExceptionHandler` наследует `ResponseEntityExceptionHandler`, поэтому и ошибки фреймворка
получают тот же конверт. В тело добавляются `timestamp` и `requestId`. Непредвиденные исключения
отдают клиенту только код запроса; сообщение уходит в лог. `RequestIdFilter` читает или генерирует
`X-Request-Id`, кладёт его в MDC и возвращает в ответе, предварительно вычищая символы, которыми
можно подделать строку структурированного лога.

Сообщения, которые формирует сам Spring, клиенту не отдаются: они на английском (нарушение NFR-8) и способны
процитировать тело запроса — ошибка разбора JSON охотно приводит телефон, на котором споткнулась (нарушение
NFR-3). Поэтому `detail` подменяется русским текстом из `ErrorCode`, а исходное сообщение уходит в лог рядом
с идентификатором запроса.

**Последствия.** Коды ошибок — часть опубликованного контракта, переименование требует ADR (§14.9).
Валидационные ответы не содержат отклонённых значений, поэтому в них не может попасть ПДн. Обратная сторона
подмены `detail`: диагностика по ответу становится грубее, и разбираться нужно по `requestId` в логах.

## ADR-0006. `docs/openapi.yaml` сверяется тестом, а не генерируется плагином

**Контекст.** §4 требует экспортировать спецификацию при сборке и коммитить её, §11 — падение
сборки при расхождении.

**Решение.** Интеграционный тест `OpenApiSpecificationIT` поднимает приложение, забирает
`/v3/api-docs.yaml` и сравнивает с закоммиченным файлом. Обновление — `make openapi`
(`./mvnw verify -Dinconsensu.openapi.update=true`). Список серверов в документе зафиксирован как `/`
(`OpenApiConfig`), иначе случайный порт тестового запуска делал бы документ нестабильным.
Включён `springdoc.writer-with-order-by-keys=true` для детерминированного порядка ключей.

**Последствия.** Не нужен отдельный запуск приложения в фазе сборки. Разработчик, изменивший API и
забывший про `make openapi`, получает красную сборку с подсказкой.

## ADR-0007. Юнит- и интеграционные тесты разведены по surefire и failsafe

**Контекст.** §11 требует и юнит-тесты доменных правил, и интеграционные тесты на Testcontainers.
Интеграционные тесты требуют Docker и заметно медленнее.

**Решение.** `*Test` — surefire (без Docker), `*IT` — failsafe (Testcontainers). Контейнер
PostgreSQL поднимается как синглтон на JVM (`AbstractIntegrationTest`), а не через
`@Container`, чтобы не перезапускать базу для каждого тестового класса. Покрытие JaCoCo
собирается из обоих прогонов в один файл.

**Последствия.** `make test` работает без Docker, `make verify` — полный цикл. Порог покрытия 80 %
применяется только к пакетам `domain` и `application` (§11).

## ADR-0008. Проверка уязвимостей зависимостей — Trivy, а не OWASP dependency-check

**Контекст.** §4 допускает «OWASP dependency-check или trivy». Dependency-check с 2023 года требует
API-ключ NVD и при каждом запуске обращается к сервису NIST.

**Решение.** В CI используется Trivy (`scan-type: fs`, severity HIGH и CRITICAL, `ignore-unfixed`).

**Последствия.** Нет зависимости от ключа и от доступности NVD, база уязвимостей может быть
зеркалирована внутрь контура (NFR-4). Проверка вынесена в отдельную job, чтобы не удлинять основную
сборку.

## ADR-0009. Версия Docker Engine API для Testcontainers вынесена в свойство

**Контекст.** `docker-java`, входящий в Testcontainers 1.20.4, по умолчанию обращается к демону с версией
API 1.32. Docker Engine 29 поднял минимально поддерживаемую версию до 1.44 и отвечает на такой запрос
`400 client version 1.32 is too old`, из-за чего падают все интеграционные тесты.

**Решение.** Свойство `inconsensu.docker.api-version` (по умолчанию `1.44`) передаётся в JVM интеграционных тестов
как системное свойство `api.version`, которое читает `docker-java`. Значение переопределяется на ходу:
`./mvnw verify -Dinconsensu.docker.api-version=1.41`.

**Последствия.** Сборка работает на Docker Engine 25 и новее из коробки. Для более старого движка или для
Podman версию нужно понизить — это одна опция командной строки, а не правка кода (NFR-4). Когда Testcontainers
начнёт согласовывать версию API самостоятельно, свойство можно будет удалить.

## ADR-0010. Интеграционные тесты помечены `@AutoConfigureObservability`

**Контекст.** Spring Boot Test по умолчанию выключает экспорт метрик в тестах
(`management.defaults.metrics.export.enabled=false`), чтобы тестовые прогоны не отправляли метрики наружу.
Из-за этого `/actuator/prometheus` в тестах отвечал 404, хотя в приложении работает, и требование NFR-6
оставалось непроверенным.

**Решение.** `@AutoConfigureObservability` поставлена на `AbstractIntegrationTest`, а не на отдельный тест:
так все интеграционные тесты имеют одинаковую конфигурацию контекста и переиспользуют один кэшированный
контекст Spring.

**Последствия.** NFR-6 проверяется тестом. Побочный эффект — в тестах включается и трассировка; если она
начнёт мешать, аннотацию можно сузить до конкретного теста ценой второго контекста.

## ADR-0011. Maven wrapper с закоммиченным jar и закреплёнными контрольными суммами

**Контекст.** §4 требует сборку через `./mvnw`, NFR-4 — работоспособность в контуре РФ. Wrapper 3.3.2 —
jar-лаунчер: при отсутствии `.mvn/wrapper/maven-wrapper.jar` он скачивает его из Maven Central без проверки
целостности. Если держать jar в `.gitignore`, чистый клон в закрытом контуре не соберётся вовсе.

**Решение.** `maven-wrapper.jar` коммитится в репозиторий, а в `maven-wrapper.properties` закреплены
`wrapperSha256Sum` и `distributionSha256Sum`. Обе суммы сверены с официальными публикациями: jar — с
`maven-wrapper-3.3.2.jar.sha1` на Maven Central, дистрибутив Maven — с `apache-maven-3.9.9-bin.zip.sha512`
на `archive.apache.org`.

**Последствия.** Чистый клон стартует без обращения к сети за лаунчером, а подмена дистрибутива Maven
обнаруживается wrapper'ом. Цена — 63 КБ бинарного файла в git и необходимость обновлять обе суммы при
смене версии Maven.

## ADR-0012. Демо-профиль не ослабляет продовые настройки

**Контекст.** `docker compose up` — это то, что заказчик увидит первым, и он запускается с профилем `demo`.
Ранее `application-demo.yml` переключал логи с JSON на текст и открывал детали health, то есть
демонстрация шла в режиме, не соответствующем NFR-6 и NFR-3.

**Решение.** В профиле `demo` остаются только демо-данные. Послабления для разработчика (читаемые логи,
подробный health) живут исключительно в профиле `dev`.

**Последствия.** Демонстрация ведёт себя так же, как эксплуатация. Разработчику для читаемых логов нужно
явно указывать профиль `dev`.

## ADR-0013. `/error` остаётся на обработчике Spring Boot до этапа 1

**Контекст.** `@RestControllerAdvice` покрывает всё, что проходит через `DispatcherServlet`, но не
покрывает `response.sendError` и сбои в фильтрах: они уходят на `/error`, где работает
`BasicErrorController` Spring Boot и отдаёт свой формат, а не `ProblemDetail` из §9. Сейчас в приложении
нет ни одного фильтра, способного так завершиться; они появятся вместе со Spring Security на этапе 1.

**Решение.** Свой `ErrorController` на этапе 0 не вводится (§14.11 — не делать будущее раньше
обязательного): он неизбежно будет переписан на этапе 7, где UI-17 требует HTML-страниц 403/404/500 и,
значит, согласования по `Accept`. Взамен `RequestIdFilter` переопределяет
`shouldNotFilterErrorDispatch()` в `false`, поэтому идентификатор запроса переживает переход на `/error`
уже сейчас.

**Последствия.** Задача для этапа 1 (вместе со Spring Security): заменить `BasicErrorController` на
обработчик, отдающий `ProblemDetail`, и на этапе 7 добавить в него согласование по `Accept` для UI-17.
До тех пор существует узкий класс ошибок, ответ на которые не соответствует §9.

## ADR-0015. Один оператор на установку, без `tenant_id`

**Контекст.** §15 требовал закрыть вопрос многотенантности до этапа 1, потому что он определяет схему целиком.

**Решение.** Заказчик ответил: многотенантность не нужна. Схема строится без `tenant_id`, реквизиты
оператора живут в `operator_settings`, для второго юрлица разворачивается отдельная установка со своей БД.

**Последствия.** Проще индексы и запросы, ниже риск утечки ПДн между тенантами, реалистичнее цели NFR-1.
Появление второго юрлица в одной установке потребует переписывания миграций, индексов, ключей
идемпотентности и всех проверок доступа — это осознанно принятая цена.

## ADR-0016. Хеш события аудита считается по всему событию, а не только по payload

**Контекст.** §6 описывает формулу `hash = SHA-256(prev_hash + канонический payload)`.

**Решение.** В хеш входит канонический вид всего события: prev_hash, тип агрегата и его идентификатор,
субъект, тип события, момент, тип и идентификатор актора и канонический payload. Поля соединяются
разделителем ASCII 0x1F, который не может встретиться в значениях, поэтому «ab|c» и «a|bc» не совпадут.

**Последствия.** Буквальная формула ТЗ оставляла бы возможность незаметно изменить тип события, актора или
время — то есть ровно то, что FR-10.1 обязан доказывать («кто, когда»). Отличие от буквы §6 задокументировано
здесь и в javadoc `AuditHashCalculator`; при сверке с внешней реализацией нужно использовать эту формулу.

## ADR-0017. Порядок записи в журнал сериализуется блокировкой по агрегату

**Контекст.** Хеш-цепочка требует, чтобы `prev_hash` нового события совпадал с хешем последнего. Две
параллельные транзакции, прочитавшие один и тот же «хвост», записали бы два события с одинаковым
`prev_hash` и раздвоили цепочку.

**Решение.** Перед чтением хвоста берётся `pg_advisory_xact_lock` по 64-битному ключу, вычисленному из
типа и идентификатора агрегата. Блокировка снимается вместе с транзакцией.

**Последствия.** Записи в разные агрегаты не ждут друг друга. Коллизия ключей возможна теоретически и
приводит лишь к лишней сериализации, а не к ошибке. Решение опирается на PostgreSQL — при смене СУБД
потребуется эквивалент.

## ADR-0018. Проверка целостности аудита пока синхронная

**Контекст.** FR-10.4 требует асинхронную проверку с идентификатором задачи и отчётом; UI-15 показывает
историю проверок. §6 не описывает таблицу для таких задач, а хранить их в памяти нельзя: приложение
stateless и масштабируется горизонтально (NFR-2).

**Решение.** На этапе 1 `POST /api/v1/audit/verify` выполняется синхронно и возвращает отчёт сразу.
Асинхронная форма с таблицей истории проверок добавляется на этапе 7 вместе с экраном UI-15.

**Последствия.** На объёмах §13 проверка занимает секунды, на 30 млн событий (NFR-1) синхронный вызов
станет неприемлемым — поэтому срок реализации асинхронной формы зафиксирован, а не оставлен на потом.

**Статус: закрыт на этапе 7** — см. ADR-0032.

## ADR-0019. Ошибка входа не различает причину, а счётчик попыток переживает откат транзакции

**Контекст.** FR-11.1 требует защиты от перебора, UI-1 — сообщения «Неверный логин или пароль» без
уточнения. При этом отказ во входе выбрасывает исключение, а `@Transactional` по умолчанию откатывает
транзакцию — вместе с инкрементом счётчика неудач, из-за чего блокировка не наступала бы никогда.

**Решение.** Неизвестный логин, неверный пароль и отключённая учётная запись дают один и тот же ответ 401,
причём для неизвестного логина всё равно выполняется сравнение хеша, чтобы время ответа не выдавало
существование пользователя. Метод входа помечен `@Transactional(noRollbackFor = ApiException.class)`.

**Последствия.** Эндпоинт нельзя использовать для перебора логинов. Счётчик и блокировка хранятся в БД,
поэтому переживают перезапуск и общие для всех экземпляров (NFR-2).

## ADR-0025. Отзыв идемпотентен, необратим и каскадируется транзитивно

**Контекст.** FR-8.3 требует идемпотентности и необратимости, FR-8.4 — каскадного отзыва зависимых типов.

**Решение.** Повторный отзыв уже отозванного согласия возвращает прежний результат и не меняет ни дату, ни
источник: клиент, нажавший кнопку дважды, не должен получить ошибку, а первая запись остаётся доказательством.
Каскад обходит зависимости транзитивно, а не на один уровень. Отозванное согласие не воскрешается: новое
согласие — это новая строка со своим идентификатором.

**Последствия.** Отзыв базового согласия гасит рекламу, передачи и распространение одной операцией, и это
видно заранее в `revocation-preview` для диалога подтверждения UI-5. Транзитивность защищает от «висящего»
разрешения, если появится тип, зависящий от рекламного.

## ADR-0081. Состояние таблиц живёт в адресной строке, сортировка — по списку разрешённых колонок

**Контекст.** UI-0.8 требует от таблиц сортировки по колонкам, пагинации 20/50/100 и хранения состояния
фильтров и страницы в query-параметрах. Имя колонки при этом приходит из адресной строки, то есть от
пользователя, и подставлять его в запрос нельзя.

**Решение.** Каждый экран объявляет карту «имя колонки в URL → свойство сущности»; `UiSorting.of`
подставляет только известные значения, всё прочее возвращает сортировку по умолчанию. Вторым ключом
сортировки всегда идёт идентификатор — иначе при равных значениях колонки одна и та же запись могла
попасть на две страницы. Ссылки сортировки, пагинации и форма выбора размера страницы собираются из
текущих параметров экрана, каждая выбрасывая ровно то, что задаёт сама.

**Последствия.** Ссылку на отфильтрованную и отсортированную таблицу можно передать коллеге. Списки-
справочники (типы согласий, третьи лица, подписки) режутся на страницы уже в памяти: они собираются со
счётчиками, которые в SQL не выражены. Сортировка карточки клиента не предусмотрена намеренно: §16
задаёт там фиксированный порядок строк — сначала истекающие, затем действующие.

## ADR-0080. Источник отзыва «Обращение в офисе» и служебные источники вне диалога

**Контекст.** UI-5 перечисляет источники обращения дословно: «письменное заявление, звонок в колл-центр,
обращение по email, обращение в офисе». В перечислении `RevocationSource` офиса не было, зато диалог
предлагал сотруднику «Личный кабинет», «Мобильное приложение» и «Каскадный отзыв» — значения, которые
проставляет система, а не оператор. Сотрудник мог записать отзыв как пришедший из личного кабинета,
и доказательство обращения теряло смысл.

**Решение.** В перечисление добавлено значение `OFFICE` («Обращение в офисе»); диалог отзыва показывает
ровно четыре источника UI-5, остальные остаются за системой (самообслуживание ставит `PERSONAL_ACCOUNT`,
каскад — `CASCADE`).

**Последствия.** Перечисление опубликовано в API, поэтому изменение отражено в `docs/openapi.yaml`:
добавление значения совместимо для читающих клиентов, но клиент, перебирающий все значения, увидит
новое. Существующие записи не затронуты.

## ADR-0079. Тестовая база очищается в начале прогона

**Контекст.** Пока интеграционные тесты поднимали контейнер, база была новой на каждый прогон. Внешняя
база (ADR-0078) живёт между прогонами и копит данные. Это не теория: очередь уведомлений накопила письма
прошлых запусков, отправка идёт пачками, и письмо текущего теста в пачку не попадало — три сценария
`NotificationEmailIT` падали на чистом коде, причём только на машине, где база уже была использована.

**Решение.** `TestDatabase.prepareOnce()` один раз на JVM пересоздаёт схему `public`, и вызывается он из
`AbstractIntegrationTest` до создания контекста; Flyway затем накатывает миграции с нуля. Тесты со своей
схемой (`ContactEncryptionIT`, `AuditJournalPrivilegesIT`) пересоздают её тем же способом.

**Последствия.** Прогон снова детерминирован и не зависит от того, что в базе осталось от предыдущего.
Плата — база из `INCONSENSU_TEST_DB_URL` полностью очищается при каждом `./mvnw verify`, поэтому она
должна быть отдельной от рабочей; в README это сказано прямо в таблице переменных. Полный накат миграций
добавляет к прогону несколько секунд — приемлемо за воспроизводимость.

## ADR-0078. Продукт ставится на чистую ОС, Docker из репозитория убран

**Контекст.** §4 ТЗ требовал многостадийный `Dockerfile` и `docker-compose.yml`, §11 — интеграционные
тесты на Testcontainers, §13 — сборку образа в CI. Заказчик решил иначе: приложение должно быть
кроссплатформенным и разворачиваться на чистой операционной системе, без установки Docker ни у
администратора, ни у разработчика. Это прямое изменение требований, а не техническое упрощение.

**Решение.** Из репозитория удалены `Dockerfile`, `docker-compose.yml`, `.dockerignore` и шаг сборки
образа в CI. Артефакт поставки — исполняемый JAR (Spring Boot) плюс юнит systemd
`deploy/inconsensu.service`; порядок установки описан в `docs/install.md`. PostgreSQL ставится штатным
пакетом ОС. Интеграционные тесты вместо Testcontainers идут на внешней базе, адрес которой берётся из
`INCONSENSU_TEST_DB_URL` / `INCONSENSU_TEST_DB_USER` / `INCONSENSU_TEST_DB_PASSWORD` (по умолчанию —
локальная `inconsensu_test`); SMTP-заглушку Mailpit заменил встроенный GreenMail, который поднимается
в самом тесте на случайном порту.

**Последствия.** Установка перестала быть однокомандной: администратору нужны JDK 21 и PostgreSQL,
поставленные заранее, — это цена отказа от контейнеров, и она осознанная. Тесты больше не создают базу
сами, поэтому `ContactEncryptionIT`, которому нужна отдельная схема с другим ключом шифрования,
изолируется схемой `encryption_test` внутри той же базы, а не своим контейнером. Сборка стала быстрее и
не зависит от доступности демона Docker и Docker Hub. Отступления от §4, §11, §12 и §13 зафиксированы
здесь и в `docs/OPEN_QUESTIONS.md`.

## ADR-0077. Конструктор форм собирает пункты, а не копирует существующие

**Контекст.** UI-8 требует список пунктов с перестановкой, кнопки «Добавить пункт» и «Удалить пункт»,
кнопку «Проверить», появление блока третьего лица по типу и предупреждение для рекламных пунктов.
Главное — кнопка «Добавить пункт» клонировала первый существующий пункт и на свежем черновике молча
ничего не делала: пунктов нет, копировать нечего. То есть **форму Приложения C нельзя было собрать в
конструкторе**, а §16.5 делает это критерием приёмки.

**Решение.** Разметка пункта вынесена во фрагмент и используется дважды: в цикле по существующим пунктам
и внутри `<template>` для нового. Дублировать её нельзя — расхождение означало бы, что добавленный пункт
теряет часть полей. Перестановка меняет узлы местами и перенумеровывает индексы в именах: порядок в
разметке и есть порядок пунктов, потому что сохранение нумерует их индексом цикла (ADR-0021).

**Последствия.** Экран соответствует UI-8. Две ловушки, стоившие времени и достойные упоминания:
у `th:replace` приоритет выше, чем у `th:each`, поэтому переменная цикла в нём недоступна — понадобился
`th:block`, а не обёртка, иначе лишний узел сломал бы перестановку соседей. И `th:inline="javascript"`
принял `[[` в регулярном выражении за своё выражение — инлайн убран за ненадобностью.

Проверка сделана браузерным тестом с включённым JavaScript: разметка сама по себе дефект не показывает,
а на прежней версии скрипта тест падает. Движок HtmlUnit не разбирает синтаксис htmx, поэтому ошибки
чужих библиотек в этом тесте не считаются отказом — проверяется собственный скрипт конструктора.

## ADR-0076. Список форм получил фильтры, которые давно поддержаны запросом

**Контекст.** UI-7 задаёт таблицу «код, название, версия, статус, источники применения, автор изменений,
дата» и пять фильтров. В таблице не было двух колонок, а из фильтров работали два: экран передавал в
`FormFilter` три `null` на месте источника, типа согласия и третьего лица — притом что сам запрос эти
условия выполняет с самого начала, а фильтр по источнику был доведён ещё в ADR-0051. Пагинации не было
вовсе, хотя список страничный: формы за первой страницей были недостижимы.

**Решение.** Три фильтра выведены на экран и передаются в запрос; добавлены недостающие колонки, выбор
размера страницы 20 / 50 / 100 и ссылки страниц, сохраняющие все фильтры в адресе (UI-0.8). Кнопки
статусов подписаны по-русски: раньше они выводили машинные коды `DRAFT`, `ON_REVIEW` (UI-0.4).

**Последствия.** Экран соответствует UI-7. Проверено на живом приложении: фильтр по неиспользуемому
источнику даёт пустой список, по договору и по типу передачи — находит форму.

## ADR-0075. Тип согласия правится из интерфейса той же формой, что и создаётся

**Контекст.** UI-6 требует «форму создания и редактирования (код задаётся только при создании)», колонку
«значимый для бизнеса» и подтверждение деактивации с числом действующих согласий. Правки из интерфейса не
было вовсе: серверная часть уже умела `update`, но ни одна страница этот признак не отправляла, поэтому
единственным действием в таблице оставалась деактивация.

**Решение.** Одна карточка на оба режима: со ссылкой «Изменить» она открывается заполненной, код
показывается только для чтения (FR-1.1 объявляет его неизменяемым). В подтверждении деактивации названо
реальное число действующих согласий — оно уже считалось для колонки счётчиков.

**Последствия.** Экран соответствует UI-6. Попутно закрыт дефект: сохранение всегда передавало
`sortOrder = 0`, и правка типа обнулила бы порядок сортировки, перемешав список в конструкторе форм.
Добавлено и поле описания — без него сохранение затирало бы его пустым.

## ADR-0073. Вкладка «История» — лента событий, а не срез согласий

**Контекст.** UI-4 описывает вкладку «История» как ленту: дата и время, описание, актор, ссылка на
согласие, фильтры по типу события и периоду, кнопка проверки целостности с указанием первого нарушенного
события. Показывался же список согласий — то есть состояние, а не история: по нему нельзя ответить, кто и
когда отозвал согласие.

**Решение.** Лента строится по журналу аудита с фильтрами; проверка целостности проходит по всем цепочкам
субъекта сразу — цепочка ведётся по агрегату, а у клиента их несколько, по одной на согласие.

**Последствия.** Экран отвечает на вопрос «что происходило с клиентом». Найденная при этом ловушка стоит
упоминания: первая версия определяла принадлежность события согласию перехватом исключения от поиска. Внутри
транзакции это её отравляет — «поймали и пошли дальше» оборачивается падением всего запроса на коммите.
Теперь тип агрегата проверяется явно, а поиск не бросает исключений. Тесты этого не показывали: они
покрывали фрагмент вкладки, а не новую точку с фильтрами, — дефект виден только на живом приложении.

## ADR-0074. Досье показывает доказательства, страница клиента — каскад отзыва

**Контекст.** UI-4a требует в досье блок «Доказательства» — поля evidence по способу подписания и ссылку на
скан; его не было вовсе, хотя досье существует ради доказуемости. UI-18 требует показывать клиенту список
каскадных отзывов до нажатия: отзывая обработку персональных данных, он гасит и рекламу, и передачи.

**Решение.** Блок доказательств отдаётся с теми же масками, что и API: телефон, OTP, IP и User-Agent
показываются как `***` (NFR-3), `documentRef` — ссылкой. Список каскада виден и в карточке согласия на
странице клиента, и в тексте подтверждения: отзыв необратим, узнавать о последствиях постфактум нельзя.

**Последствия.** Оба экрана соответствуют §16. Проверено на живом приложении: маски на месте, список
каскада строится по тому же правилу FR-8.4, что и сам отзыв.

## ADR-0071. Индикаторы каналов в поиске строятся по уже загруженному субъекту

**Контекст.** FR-5.2 требует фиксировать поиск в журнале доступа к ПДн одной записью. Фактически их было
больше: колонка индикаторов каналов в строке результата вызывала карточку по идентификатору, а та
перечитывает субъекта — и каждое такое чтение писало собственную запись. Один поиск оставлял в журнале
одну запись плюс по записи на каждую найденную строку, то есть журнал переставал отвечать на вопрос
«к скольким клиентам обращались».

**Решение.** Карточка строится по уже загруженному объекту субъекта — перегрузка без повторного чтения.
Запись в журнал остаётся ровно одна, на сам поиск.

**Последствия.** Журнал доступа снова отражает действительность. Побочно ушла лишняя работа: страница
результатов больше не перечитывает каждого субъекта.

## ADR-0072. Карточка показывает текст согласия, заменённые записи и истёкший договор

**Контекст.** UI-4 перечисляет во вкладке «Согласия» действие «Текст согласия», переключатель «Показать
заменённые» и пометку об истёкшем договоре третьего лица. Ни одного из трёх не было: сотрудник видел
название типа, но не документ, под которым расписался клиент, не мог посмотреть историю замен и не узнавал,
что передача идёт по согласию, срок договора с получателем которого уже вышел.

**Решение.** Текст версии открывается модальным окном с номером версии, датой публикации и контрольной
суммой вместе с результатом сверки. Заменённые скрыты по умолчанию — иначе таблица у давнего клиента
разрастается историей, а нужен текущий срез — и добавляются переключателем. Признак истёкшего договора
считается в строке согласия и показывается бейджем.

**Последствия.** Экран соответствует UI-4. Проверено на живом приложении: в текст версии входят оба
обязательных блока ч. 4 ст. 9 и все пункты, контрольная сумма сходится.

## ADR-0069. Импорт читает справочники один раз на задачу

**Контекст.** Критерий §13 «импорт 100 000 строк в тесте проходит» не был закрыт, а `performance.md`
утверждал обратное. Замер показал худшее: пробный прогон 10 000 строк занимал 114 секунд — около
87 строк в секунду при цели NFR-1 в 5 000. Каждая строка перечитывала тип по коду, все версии формы,
саму форму ещё раз при разборе пункта и третье лицо по ИНН; часть этих чтений добавил перенос проверки
FR-2.3 на путь импорта (ADR-0055).

**Решение.** Кэш справочников на один прогон задачи: тип, форма и третье лицо читаются один раз.
Живёт ровно столько, сколько идёт задача, — справочник могли изменить между импортами, а общий кэш
пришлось бы инвалидировать. Форма, уже найденная при разборе строки, передаётся в регистрацию, а не
загружается там снова.

**Последствия.** Пробный прогон 10 000 строк — 1,97 секунды (≈5 080 строк/с), в 58 раз быстрее: цель
NFR-1 для разбора и проверки достигнута. Приёмочный тест §13 на 100 000 строк добавлен и выполняется в
пробном режиме.

**Что осталось.** Запись в базу цели не достигает: ≈31 строка в секунду. На строку приходятся upsert
субъекта, вставка согласия, событие аудита с чтением предыдущего хеша цепочки, запись в outbox и запрос
на замещение — и всё в отдельной транзакции, которой требует FR-4.5. Цифры обеих ветвей записаны в
`performance.md`, вопрос о пакетной записи вынесен в `OPEN_QUESTIONS.md` (вопрос 19): она несовместима с
построчной транзакцией, поэтому решать его без заказчика нельзя.

## ADR-0070. Поиск субъектов принимает явные признаки, а не только единое поле

**Контекст.** §9 описывает `GET /subjects` с параметрами `query`, `phone`, `email`, `externalId`.
Реализован был только `query` с эвристикой UI-3, три параметра из контракта игнорировались молча:
внешний потребитель, следующий §9, получал поиск, не замечающий переданное значение.

**Решение.** Явные признаки добавлены и имеют приоритет над `query`. Единое поле остаётся: оно нужно
интерфейсу, где сотрудник вводит что попало. Машинный клиент знает, что у него на руках, и не должен
зависеть от эвристики.

**Последствия.** Контракт §9 выполняется целиком. Каждый вызов, как и прежде, пишется в журнал доступа
к ПДн одной записью (FR-5.2).

## ADR-0066. Доказательства проверяются не только на наличие, но и на формат

**Контекст.** Таблица FR-4.2 задаёт для SMS-подписи телефон в формате E.164. Проверялось только то, что
поле не пустое, поэтому доказательство сохранялось в виде «8 916 …» или даже «телефон клиента»:
формально заполнено, но сопоставить с абонентом нельзя — как доказательство подписания оно не работает.

**Решение.** Неверный формат отделён от отсутствия поля: сообщения у них разные, и валидатор возвращает
их отдельными списками. Обе проверки собраны в один ответ, чтобы клиент увидел все замечания сразу
(FR-1.3 требует того же от валидатора формы).

**Последствия.** Регистрация с телефоном в произвольном виде отклоняется с указанием поля и примера.
Импорт исторических согласий не затронут: там способ подписания IMPORTED_LEGACY, и телефон не требуется.

## ADR-0067. Предупреждение о специальных категориях ПДн смотрит на состав пункта, а не на число пунктов

**Контекст.** FR-1.4 требует предупреждать, когда «специальные категории ПДн включены в общий пункт».
Условие проверяло, что в форме больше одного пункта, — то есть срабатывало как раз на правильном
оформлении, когда специальные категории вынесены в отдельный чистый пункт, и молчало о настоящем
нарушении, если форма состояла из одного смешанного пункта. Существующий тест закреплял это поведение.

**Решение.** Признак вычисляется по составу пункта: специальные (или биометрические) категории вместе с
обычными внутри одного пункта. Тест переписан, добавлен случай «специальные категории в отдельном пункте
— не предупреждение».

**Последствия.** Юрист перестаёт получать предупреждение на корректной форме и получает его там, где
категории действительно смешаны.

## ADR-0068. Предупреждения валидатора сохраняются в журнале и в событии аудита

**Контекст.** FR-1.4 требует, чтобы предупреждения «не блокировали, но выводились и логировались». Вывод
в панели конструктора был, логирования не было: после отправки формы на согласование след предупреждений
не оставался нигде.

**Решение.** При отправке предупреждения пишутся в журнал приложения и попадают в payload события
FORM_SUBMITTED. Событие уже неизменяемо и связано с формой, поэтому отдельного хранилища не нужно.

**Последствия.** Видно, что согласующим показывали форму с предупреждением и его приняли осознанно.

## ADR-0064. Форма входа считает неудачные попытки через события Spring Security

**Контекст.** FR-11.1 и UI-1 требуют блокировать учётную запись после N неудачных попыток. Счётчик
наращивал только REST-вход: он сверяет пароль вручную и потому делает это сам. Форму интерфейса
обрабатывает стандартный провайдер, который лишь читает готовый признак блокировки, — через `/ui/login`
пароль можно было подбирать без ограничений. Вдобавок форма всегда вела на `?error`, поэтому ветка
страницы «слишком много попыток» была недостижима, и сотрудник видел «неверный логин или пароль».

**Решение.** Слушатель событий аутентификации наращивает счётчик при неудаче и сбрасывает при успехе.
Реагирует только на вход логином и паролем: события проверки JWT к перебору отношения не имеют, а их учёт
сбрасывал бы счётчик на каждом запросе к API. Двойного счёта нет — REST-путь событий не публикует.
Обработчик отказа добавляет к адресу срок блокировки, и страница показывает «повторите через M мин.».

**Последствия.** Перебор через интерфейс ограничен той же настройкой, что и через API. Срок берётся у
`AuthService`, а не из репозитория напрямую: §5 запрещает модулю `ui` видеть инфраструктуру чужого модуля,
и ArchUnit это поймал на первой попытке.

## ADR-0065. Порты SignatureProvider и DocumentStorage заведены с реализациями по умолчанию

**Контекст.** §3 прямо требует предусмотреть два порта расширения: `SignatureProvider` с
реализацией-заглушкой (УКЭП вне объёма) и `DocumentStorage` с реализацией на локальной ФС для dev. В коде
не было ни одного из них — имена встречались только в документации.

**Решение.** Оба интерфейса заведены в `common.integration`. Заглушка проверки УКЭП честно отказывает, а не
возвращает «подпись верна»: доказательство, которое никто не проверял, хуже отсутствующего. Хранилище на
локальной ФС отдаёт только метаданные — содержимое наружу не выходит, чтобы скан не утёк вместе с
карточкой, — и нормализует ссылку: её заполняет внешняя система, и «../» не должно выводить за пределы
каталога. Обе реализации уступают место бину заказчика.

**Последствия.** Подключение криптопровайдера или СЭД не потребует правки доменной логики. Проверка
`documentRef` через хранилище пока не включена в валидацию доказательств: адрес хранилища заказчика
неизвестен (открытый вопрос 3), и обязательная проверка сделала бы импорт неработоспособным.

## ADR-0062. Служебная роль INTEGRATION ограничена матрицей Приложения E

**Контекст.** На контроллерах каталога, форм, справочника третьих лиц и субъектов стояло
`@PreAuthorize("isAuthenticated()")`, поэтому служебная учётная запись INTEGRATION читала всё это наравне
с сотрудниками. Приложение E даёт ей «нет» по каталогу, формам и третьим лицам, а карточку — только по
`external_id`; UI-0.3 прямо называет её служебной и не пускает даже в интерфейс.

**Решение.** Введено выражение `Authorities.EMPLOYEE` — все роли, кроме INTEGRATION; выражение
`@PreAuthorize` обязано быть константой времени компиляции, поэтому роли перечислены строками в одном
месте. Оно закрывает каталог, формы, статистику с выгрузкой и справочник третьих лиц, а в модуле
субъектов — поиск и обращения по внутреннему идентификатору. Регистрация согласий, upsert субъекта и
доступ по `external_id` службе оставлены: без них интеграция не работает.

**Последствия.** Токен интеграции больше не даёт выгрузить каталог или карточку по перебору UUID.
Матрица закрыта тестом, перечисляющим закрытые пути.

## ADR-0063. Досье показывает пункт формы, карточка — роль третьего лица

**Контекст.** FR-10.3 перечисляет в досье «точный текст формы и checksum, **пункт**, данные подписания,
все события». Пункта не было: досье показывало текст версии целиком, но не то, под чем именно
расписался клиент. Отдельно, Приложение A содержит роль третьего лица рядом с именем, а ответ карточки её
не отдавал, хотя §13 делает совпадение с макетом критерием приёмки этапа 3.

**Решение.** В досье добавлен блок пункта: тип, формулировка, цели, категории ПДн, срок и признак
обязательности. В согласии карточки рядом с именем третьего лица отдаётся его роль — обработчик по
поручению, самостоятельный получатель или компания экосистемы: это разные основания передачи.

**Последствия.** Доказательство отвечает на вопрос «на что именно согласился клиент», а не только «какой
документ он видел». Оба поля добавлены к ответам, разбор у существующих клиентов не ломается;
`docs/openapi.yaml` перегенерирован.

## ADR-0060. Секрет подписки webhook шифруется тем же механизмом, что и контакты

**Контекст.** §6 прямо помечает `webhook_subscription.secret` как шифруемое поле — единственное такое поле
в перечне. Хранился он открытым текстом: в миграции стоял комментарий «шифрование — этап 8», но этап 8
закрыт, а механизм (`CryptoService` + `EncryptedStringConverter`) давно применён к контактам субъекта.
Секрет позволяет подделать подпись доставки, поэтому дамп базы означал бы компрометацию всех подписок.

**Решение.** На поле навешен тот же конвертер, ширина колонки увеличена под шифртекст отдельной миграцией.
Значения не переписываются: конвертер отдаёт строку без префикса `enc:v1:` как есть, поэтому заведённые
раньше подписки продолжают работать и получают шифрование при первом сохранении.

**Последствия.** Секрет защищён тем же ключом и той же процедурой ротации, что и контакты. Как и для
контактов, шифрование действует при включённом `inconsensu.crypto.enabled`.

## ADR-0061. Предел страницы, CORS и пользователь в логах заданы настройками

**Контекст.** Три требования оказались не выполнены, причём каждое выглядело выполненным. §9 задаёт
максимум `size = 200`, но предела не было нигде — действовало умолчание Spring Data, равное 2000, и один
запрос мог выгрузить разом слишком много ПДн. NFR-3 требует настраиваемый CORS; в цепочке стоял
`cors(withDefaults())`, который молча берёт конфигурацию из аннотаций, а их в проекте нет — настроить
CORS было нельзя вовсе, а правило `permitAll` для `OPTIONS` создавало видимость обратного. NFR-6 требует
в логах `request id` и `user id`; в MDC попадал только первый.

**Решение.** `spring.data.web.pageable.max-page-size: 200`. Источник CORS — бин с настройками
`inconsensu.security.cors.*`, по умолчанию не разрешён ни один источник: интерфейс и API живут на одном
домене, а доступ из чужого источника оператор включает осознанно. Пользователь кладётся в MDC отдельным
фильтром: тот, что ставит `requestId`, работает первым, до цепочки безопасности, и на его этапе
пользователь ещё неизвестен.

**Последствия.** В журнал попадает логин сотрудника, а не данные субъекта — NFR-3 не нарушен. Клиент,
запросивший больше 200 записей, получает страницу в 200, а не отказ: §9 задаёт предел, а не ошибку.

## ADR-0059. Строка дайджеста дополняется до полного набора колонок

**Контекст.** Письмо-сводка FR-9.2 собирается из очереди уведомлений, а набор полей у них разный: у письма
об истечении есть срок действия, у письма об отзыве его нет. Thymeleaf на отсутствующем ключе карты не
возвращает `null`, а бросает исключение, поэтому одно «чужое» уведомление в группе срывало всю сводку
целиком. Дефект проявился только в CI: локально порядок классов не сводил такие уведомления в одну группу.

**Решение.** Перед рендером строка дополняется до полного набора колонок дайджеста, недостающие значения —
пустые. Тот же список колонок используется и для CSV-вложения, чтобы таблица письма и файл не разошлись.

**Последствия.** Сводка переживает любое сочетание поводов, а не только те, что были на момент написания
шаблона. Уведомление, чьи данные не разобрались, попадает в письмо пустой строкой, но не роняет рассылку
остальным.

## ADR-0055. Правило FR-2.3 применяется и на пути импорта

**Контекст.** Проверка «регистрировать можно только по опубликованной действующей версии» стояла лишь в
обычной регистрации. Импорт шёл мимо неё и подбирал версию по номеру в любом статусе — согласие можно
было привязать к черновику, который никто не согласовывал и не публиковал. Без номера версии бралась
текущая опубликованная, а разрешённая ТЗ архивная версия, действовавшая на дату согласия, не находилась
вовсе.

**Решение.** Проверка перенесена в общий путь: `registerImported` вызывает то же правило. Без номера
версии импорт подбирает версию, действовавшую на `granted_at`, включая архивную. Окно действия
опубликованной версии для `source = CLIENT_BASE_IMPORT` не проверяется: формы заводятся при внедрении и
получают `valid_from` = момент публикации, поэтому строгая сверка отвергала бы весь перенос ранее
собранных согласий. Статус проверяется всегда.

**Последствия.** Ссылка на черновик отклоняется с построчной ошибкой в отчёте импорта. Вопрос о том,
нужно ли заводить версии форм задним числом ради строгой сверки дат, вынесен в `OPEN_QUESTIONS.md`
(вопрос 18) — ответ потребует возможности задавать `valid_from`, которой сейчас нет.

## ADR-0056. Уведомления по отзыву и выдаче ставятся по событию, а не ежедневной задачей

**Контекст.** FR-8.5 требует извещать DPO о прекращении обработки, а §6 перечисляет `GRANTED` и `REVOKED`
среди поводов `notification_rule.trigger`. Этих значений в перечислении не было: правило на отзыв нельзя
было ни создать, ни обработать, и единственным следствием отзыва оставалось событие в outbox для внешних
систем. Кроме того, условие правила `third_party_id` не участвовало в отборе вовсе — суженное правило
рассылало уведомления по всем согласиям и договорам.

**Решение.** Добавлены поводы `GRANTED` и `REVOKED`. Отзыв — событие, а не состояние, которое можно найти
ежедневным обходом: ч. 5 ст. 21 152-ФЗ отсчитывает тридцать дней от момента отзыва, поэтому письма
ставятся в очередь слушателем доменного события, в транзакции издателя — как и запись в outbox. Условие
`third_party_id` уходит в запрос наравне с типом согласия. Событие отзыва дополнено идентификатором и
названием типа: без них правило нечем сузить, а письмо нечем заполнить. Имя партнёра в событие не
попадает — обращаться из `registry` в `thirdparty` нельзя, зависимость инвертирована (ADR-0023).

**Последствия.** DPO узнаёт об отзыве сразу. Состав события webhook расширен новыми полями — это
дополнение контракта, разбор у потребителей не ломается. `docs/openapi.yaml` перегенерирован.

## ADR-0057. Договор третьего лица уведомляет и о самом факте истечения

**Контекст.** FR-7.1 требует, чтобы при `contract_valid_until < now` DPO получал уведомление. Реализован
был только предупреждающий порог «за N дней»: выборка шла окном от сегодняшнего дня, а истёкший договор
в него не попадает ни при каком пороге, включая ноль.

**Решение.** Отдельная выборка уже истёкших договоров, обрабатываемая тем же правилом. Порог такого
уведомления — минус один: он отличает «договор закончился» от предупреждения и не сталкивается с
дедупликацией по порогам.

**Последствия.** Ответственный узнаёт и о приближении срока, и о том, что он прошёл.

## ADR-0058. Подставной приёмник webhook читает тело байтами

**Контекст.** Как только в тело события попал русский текст (название типа согласия), доставка стала
обрываться: `Request cancelled`. Событие уходило в повтор, а следующее событие того же согласия ждало его
по правилу сохранения порядка FR-9.3 — до подписчика доходило одно письмо вместо двух.

**Решение.** Дефект оказался в тестовом стабе, а не в коде: он читал `Content-Length` — число байтов — и
затем вычитывал столько же символов из UTF-8-ридера. На латинице это совпадало, на кириллице символов
меньше, чем байтов, стаб ждал недостающие и не отвечал вовсе. Теперь тело читается байтами и декодируется
после. Заодно отправитель задаёт кодировку явно и отправляет байты UTF-8: подпись HMAC считается по ним
же, и совпадение перестало зависеть от умолчаний конвертера.

**Последствия.** Кириллица в событиях проверяется тестами по-настоящему. Заголовок `Content-Type` теперь
`application/json;charset=UTF-8` — уточнение опубликованного контракта, разбор у потребителей не меняется.

## ADR-0054. Контрольная сумма формы покрывает документ целиком

**Контекст.** FR-1.6 требует контрольную сумму канонического рендера формы, а FR-1.5 объявляет
неизменяемыми «текст, пункты, реквизиты». Считалось же только тело: `renderCanonical` принимал `body` и
ничего больше. Две версии, различающиеся обязательными блоками ч. 4 ст. 9 152-ФЗ («перечень действий и
способов обработки», «срок действия и порядок отзыва») или составом пунктов — формулировками, целями,
категориями ПДн, третьим лицом, сроком, — давали одинаковую сумму. Тот же неполный текст отдавал и
`GET /forms/{id}/text`, то есть «точный текст версии на момент подписания» им не был.

**Решение.** Канонический рендер собирает версию целиком: тело, оба обязательных блока и пункты по
порядку с их условиями. Перестановка пунктов меняет документ и сумму — нумерация в тексте другая.

**Последствия.** Доказательство описывает те условия, на которых клиент дал согласие. Уже выданные
согласия не затронуты: `canonicalText` отдаёт текст, сохранённый при публикации (`rendered_text`), и
сумма по нему пересчитывается прежней. Исключение — формы, опубликованные до появления `rendered_text`:
у них поле пустое, текст пересобирается заново, и в досье сверка покажет расхождение. Установок в
эксплуатации нет, поэтому миграция данных не делалась.

## ADR-0052. Поисковый запрос хранится в сессии, в адресную строку уходит только идентификатор

**Контекст.** UI-0.10 требует, чтобы в URL были только UUID, а §16.5 повторяет это как критерий приёмки.
Поиск клиента при этом отправлялся методом GET, и телефон, email или ФИО оказывались в адресной строке,
истории браузера, заголовке `Referer` и журналах прокси. Ссылки пагинации повторяли значение ещё и в
разметке.

**Решение.** Обе формы поиска — глобальная в шапке и на странице клиентов — отправляются методом POST.
Критерий сохраняется в серверной сессии под случайным UUID, и происходит переход на
`/ui/subjects?searchId=<uuid>`; ссылки пагинации ведут по нему же. Хранятся десять последних запросов:
сессия живёт до получаса, и без предела список рос бы на каждый поиск. Если идентификатор неизвестен
(сессия истекла, ссылку открыли в другом сеансе), страница показывает подсказку «Запрос устарел», а не
ошибку.

**Последствия.** ПДн не покидают тело запроса и ответа. Ссылку с результатами больше нельзя переслать
коллеге — это и есть цель требования. Отдельная таблица не понадобилась: интерфейс и так работает на
серверной сессии (UI-0.3).

## ADR-0053. Идемпотентность регистрации подтверждается квитанцией, а не наличием согласий

**Контекст.** FR-4.1 требует, чтобы повтор запроса с тем же `Idempotency-Key` возвращал исходный
результат с кодом 200. Признаком повтора служило наличие согласий с этим ключом, но запрос, все пункты
которого отклонены, согласий не создаёт: повтор выполнялся заново, отвечал 201 и писал в журнал вторые
события DECLINED. Вдобавок ветка повтора возвращала пустой список отклонённых пунктов, поэтому при
частичном отказе повторный ответ отличался от исходного.

**Решение.** Таблица `registration_receipt` фиксирует обработанный ключ и состав отклонённых пунктов.
Повтор опознаётся по ней, а согласия подтягиваются как прежде. Таблицы нет в перечне §6 — отклонение
зафиксировано здесь.

**Последствия.** Повтор идемпотентен при любом составе решений, включая полный отказ; ответ совпадает с
исходным. Цена — одна запись на запрос регистрации.

## ADR-0050. Статистика и выгрузка каталога считают по всем типам, а не только по активным

**Контекст.** Сверка с ТЗ показала: разрез `byType` в `/catalog/stats` и выгрузка `/catalog/export`
перечисляли типы через `activeTypes()`, тогда как сами согласия считались по всей таблице. После
деактивации типа его действующие, истекающие и отозванные согласия исчезали из отчётов, хотя FR-1.1
прямо требует, чтобы они продолжали действовать и учитываться, а §6 запрещает удалять справочники.
Сумма по разрезу переставала сходиться с плиткой «действующие», а колонка `active` в CSV всегда была
`true` и не несла смысла.

**Решение.** Статистика и выгрузка перечисляют справочник целиком (`allTypes()`). Конструктор форм и
эндпоинт справочников по-прежнему предлагают только активные типы: FR-1.1 запрещает использовать
неактивный тип в новых формах.

**Последствия.** Отчёты сходятся, колонка `active` стала осмысленной. Регрессия закрыта тестом на
собственном типе: деактивация seed-типа осталась бы в общей базе и повлияла бы на соседние классы.

## ADR-0051. Фильтр форм по источнику выполняется запросом через array_position

**Контекст.** FR-3.1 требует фильтровать формы по источнику применения вместе с пагинацией. Условие
единственное из всех применялось к уже выбранной странице, а `PageImpl` получал `totalElements` от
неотфильтрованного запроса: подходящие формы с других страниц не показывались, размер страницы был
меньше запрошенного, а число страниц завышено.

**Решение.** Источники хранятся столбцом `text[]`, поэтому вхождение выражено функцией `array_position`
прямо в `Specification`. Сравнение с нулём, а не проверка на `null`: Hibernate оборачивает функцию в
`coalesce(..., 0)`, из-за чего `is not null` истинно всегда и фильтр молча исчезает — это и показал
сгенерированный SQL при первой попытке.

**Последствия.** Число страниц и постраничный обход корректны. Тест берёт источник, которым не
пользуется ни одна форма: прежняя реализация возвращала для него общее число форм, а не ноль.

## ADR-0049. Spring Boot поднят до 3.5.16 ради NFR-3

**Контекст.** Job проверки зависимостей в CI не работал с самого начала: сначала не разрешался тег
`trivy-action@0.28.0`, а после починки выяснилось, что релизы до v0.33 ссылаются на `setup-trivy` по
тегу, а те теги удалены из репозитория. Как только сканирование заработало, оно нашло 43 уязвимости
(31 HIGH, 12 CRITICAL) в управляемых зависимостях Spring Boot 3.4.1. Ветка 3.4 закрыть их не может:
CRITICAL в `spring-security-web` исправлен только начиная с 6.5.9, а 3.4.x управляет 6.4.x.

**Решение.** Spring Boot 3.4.1 → 3.5.16 (§4 ТЗ требует «3.3+», так что ограничение соблюдено) и
переопределение версии драйвера PostgreSQL до 42.7.13: управляемая 42.7.11 остаётся уязвимой. Версия
trivy-action поднята до v0.36.0 — там ссылка на `setup-trivy` закреплена по SHA, который удалить нельзя.
Потребовалась одна правка кода: с 3.5 планировщик тоже является `TaskExecutor`, и внедрение по типу в
`AfterCommitExecutor` стало неоднозначным — пул задан явным квалификатором.

**Последствия.** Сканирование даёт ноль HIGH и CRITICAL, проверено локально теми же флагами, что в CI.
Все 417 тестов зелёные. Обновление минорной версии фреймворка — не патч: при следующем обновлении
сверяться с примечаниями о совместимости, а `CLAUDE.md` теперь называет 3.5.

## ADR-0047. Часы приложения округляются до микросекунды

**Контекст.** Прогон CI на Linux показал шесть падений, которых нет на macOS: цепочка аудита отвечала
BROKEN в `AuditJournalIT` и `ConsentRegistrationIT`, а `RevocationIT` сравнивал
`...430564177Z` с `...430564Z`. Причина одна: `Clock.system` на Linux наносекундный, а `timestamptz`
хранит микросекунды. Мгновение менялось при обращении к базе. Хеш события FR-10.1 считается по
`occurred_at`, поэтому пересчёт при чтении никогда не совпадал с сохранённым — на целевой платформе
(NFR-4, Alt Linux) проверка целостности рапортовала бы BROKEN по каждому событию. На macOS системные
часы и так микросекундные, и локальная сборка дефект не показывала.

**Решение.** Бин `Clock` округляется до разрешения базы: `Clock.tick(..., Duration.ofNanos(1000))`.
Точка одна — прямых `Instant.now()` в коде нет, всё время берётся из `Clock`. Усечение вынесено в
отдельный метод и проверяется юнит-тестом на заведомо наносекундных часах: иначе тест проходил бы на
macOS независимо от исправления и ничего не гарантировал.

**Последствия.** Мгновение переживает обращение к базе без изменений, доказуемость §1 п. 4 работает на
целевой платформе. Точность «now» ограничена микросекундой — для сроков согласий и порогов уведомлений
это несущественно.

## ADR-0048. Тест шифрования контактов работает на собственной базе

**Контекст.** Интеграционные тесты делят один контейнер PostgreSQL, чтобы не перезапускать базу на каждый
класс. `ContactEncryptionIT` включает шифрование, а проход ротации ключа переписывает все контакты базы,
какие в ней есть, — не только созданные этим классом. Соседние классы работают с выключенным флагом и на
чужом шифртексте падают в конвертере: так на Linux ломался `DemoDataIT`, тогда как на macOS порядок
классов был иным и дефекта не было. Точечная уборка после теста проблему не сняла: режим хранения
глобален, и достаточно одной строки, дописанной между уборкой и следующим классом.

**Решение.** Класс получил собственный контейнер PostgreSQL и не наследует общий. Изолируется хранилище
целиком, а не отдельные строки. Заодно фамилия субъекта в тесте больше не совпадает с демо-субъектом
«Бондаренко С. А.» из §11.

**Последствия.** Порядок классов перестал влиять на результат, и никакая будущая правка теста шифрования
не сможет задеть остальную суиту. Цена — один дополнительный запуск контейнера, около десяти секунд:
это дешевле, чем плавающее падение, воспроизводимое только на одной платформе.

## ADR-0046. Переименование в миграциях откачено: применённые файлы восстановлены

**Контекст.** ADR-0044 переименовал систему сквозь весь репозиторий, и под замену попали восемь уже
закоммиченных миграций Flyway: в них были переписаны `COMMENT ON` и seed-ключи `operator_settings`
(`cus.*` → `inconsensu.*`). Это прямо запрещено §14.5 ТЗ и `CLAUDE.md`. Парадокс в том, что тем же
коммитом добавлена миграция `V202608260000`, в шапке которой написано «прежние миграции неизменяемы».
Практическое последствие — расхождение контрольных сумм: на базе, где старые версии уже применены,
`flyway validate` останавливает запуск приложения.

**Решение.** Восемь файлов восстановлены до содержимого коммита `cdafe19^`. Конечное состояние базы
обеспечивают отдельные шаги: ключи настроек переименовывает `V202608260000`, комментарии схемы —
новая `V202608270000`. Схема при этом не меняется.

**Последствия.** Контрольные суммы применённых миграций снова совпадают, правило §14.5 восстановлено.
На чистой базе seed по-прежнему вставляет ключи `cus.*`, а следующая миграция сразу переименовывает их —
конечный набор настроек тот же. Цена — исходный текст старых миграций содержит прежнее имя продукта;
это осознанно: миграция есть исторический документ и переписыванию не подлежит.

## ADR-0045. Каталог выгружается целиком в JSON и по частям в CSV

**Контекст.** FR-3.3 требует экспорта каталога — типов, форм и пунктов — в JSON и CSV. Раньше выгружались
только типы со счётчиками. У типов, форм и пунктов разный набор колонок, и одной таблицей они не
описываются: склейка трёх заголовков в один файл нечитаема ни человеком, ни Excel.

**Решение.** `GET /catalog/export?format=json` отдаёт каталог целиком: типы, формы и вложенные пункты
одним документом. `format=csv` отдаёт одну таблицу — часть выбирается параметром `part` со значениями
`types` (по умолчанию), `forms`, `items`. В интерфейсе выгрузка живёт на `/ui/catalog/export`: цепочка
безопасности §12 требует для `/api/**` токен, и браузер с сессионной кукой получил бы там 401.

**Последствия.** Прежние ссылки `?format=csv` продолжают отдавать таблицу типов, то есть контракт
расширен, а не сломан. Полная выгрузка каталога одним файлом доступна только в JSON; получателю CSV
нужно скачать три файла. Обратимо: при необходимости добавится `format=zip` с тремя таблицами внутри.

## ADR-0044. Система переименована в «In consensu», пакет — `ru.example.inconsensu`

**Контекст.** Заказчик дал системе имя «In consensu». Вопрос 10 `OPEN_QUESTIONS.md` (корневой пакет,
ADR-0003) оставался открытым, а рабочее имя «ЦУС» встречалось в пакете, настройках, метриках, именах
контейнеров и в текстах интерфейса.

**Решение.** Переименование сквозное: пакет `ru.example.cus` → `ru.example.inconsensu`, префикс настроек
`cus.*` → `inconsensu.*`, переменные окружения `CUS_*` → `INCONSENSU_*`, ключи `operator_settings`
(миграция `V202608260000`), метрики `inconsensu.*`, артефакт, образ, контейнеры, том, база и пользователь
БД. Контракт на проводе тоже переименован: заголовки `X-InConsensu-Event`, `X-InConsensu-Delivery-Id`,
`X-InConsensu-Signature`, `X-InConsensu-File-Checksum`, тип ошибки `urn:inconsensu:error:`, User-Agent
`InConsensu-Webhook/1.0`. `docs/TZ.md` не трогается: это исходный документ заказчика. Репозиторий на
GitHub переименован заказчиком в `In_consensu`, remote `origin` переставлен на новый адрес.

**Последствия.** Смена заголовков и типа ошибки — изменение опубликованного контракта (§14.9): потребители
webhook и клиенты API обязаны обновить разбор заголовков и сверку `type` в ProblemDetail; `docs/openapi.yaml`
и `docs/webhooks.md` перегенерированы и обновлены. Развёрнутые стенды требуют новых переменных окружения и
базы `inconsensu`; ключи настроек переносит миграция, данные не теряются.

## ADR-0043. Правило «нет базового согласия — нельзя» распространено на передачи и выгрузки

**Контекст.** §8.3 п. 3 требует живого согласия `PDN_PROCESSING` и для каналов, и для передач. Расчёт
передач и выгрузка партнёру этого не проверяли: разрешение выдавалось по одному лишь согласию на передачу,
поэтому после отзыва базового согласия данные субъекта продолжали уходить партнёру.

**Решение.** `SubjectTransferPort` получил `baseConsentUsable(subjectId)`; без живого базового согласия
`TransferEvaluator` возвращает пустой список и отказ с причиной «нет действующего согласия на обработку
ПДн», а `RegistryPartnerExportProvider` пропускает таких субъектов при формировании файла.

**Последствия.** Отзыв базового согласия немедленно останавливает и передачи, и выгрузки — как того
требует ч. 5 ст. 21 152-ФЗ. Ошибка была найдена сплошной сверкой реализации с ТЗ, а не тестами: все
частные правила выполнялись, отсутствовала связка между ними.

## ADR-0042. При расхождении §9 и Приложения E выбрано более строгое прочтение прав

**Контекст.** §9 разрешает `POST /channels/check` ролям MANAGER, MARKETING, INTEGRATION, DPO и ADMIN.
Приложение E для MANAGER указывает только одиночную проверку, а массовую — для MARKETING и INTEGRATION.
Оба требования из одного документа и противоречат друг другу.

**Решение.** Массовая проверка (`/channels/check`, `/channels/check-async` и выгрузка файла) доступна
MARKETING, INTEGRATION, DPO, ADMIN. Одиночная проверка канала и точечная проверка передачи остаются
доступны MANAGER. Расхождение записано вопросом 18.

**Последствия.** Менеджер колл-центра не может выгрузить список «кому можно звонить» по всей базе — это
согласуется с принципом наименьших привилегий. Если заказчик подтвердит обратное, роль возвращается одной
строкой аннотации, контракт при этом не меняется.

## ADR-0041. Массовая проверка получила асинхронную форму, синхронный предел сохранён

**Контекст.** FR-6.4 ограничивает синхронную проверку 10 000 идентификаторов. Рассылке нужен ответ по всей
базе, а держать HTTP-соединение на время такой проверки бессмысленно.

**Решение.** Добавлены `POST /api/v1/channels/check-async` и `GET /api/v1/channels/check-async/{jobId}`.
Задача считается порциями по 10 000 тем же кодом, что и синхронный вызов, состояние хранится в
`bulk_check_job`. Синхронный эндпоинт и его предел не изменились.

**Последствия.** Ответ по миллиону идентификаторов возможен без изменения контракта существующего вызова.
Расхождений между синхронной и асинхронной проверкой быть не может: правило §7.6 вычисляет один и тот же код.

## ADR-0040. Нагрузочный smoke выполняется в обычной сборке

**Контекст.** §13 требует нагрузочный smoke и подтверждение целей NFR-1 отчётом. Отдельный стенд с Gatling
означал бы новую зависимость (§14.8) и прогон, который никто не запускает.

**Решение.** Тест `PerformanceSmokeIT` работает в общей сборке на Testcontainers: наполняет базу
вымышленными данными, измеряет p95 ключевых операций, снимает планы выполнения и пишет
`target/performance-report.md`. Пороги теста мягче целей NFR-1, чтобы прогон не зависел от загрузки машины.

**Последствия.** Первый же прогон нашёл две ошибки: чтение настройки «порог истечения» на каждое согласие и
проверку существования субъекта по одному идентификатору. Обе исправлены, массовая проверка ускорилась с
3,4 с до 272 мс на 2 000 записей. Объём прогона (2 000 субъектов) меньше проектного, поэтому цели NFR-1
подтверждены только на этом масштабе — это прямо сказано в `docs/performance.md`.

## ADR-0039. Ретенция архивирует согласия, но не трогает журнал аудита

**Контекст.** NFR-5 требует настраиваемую политику архивации, FR-10.2 — append-only журналы на уровне базы.
Автоматическая задача с правом удалять события противоречила бы второму требованию.

**Решение.** Ночная задача (по умолчанию выключена) переносит отозванные согласия старше срока в
`consent_archive`, очищает тела истёкших выгрузок и удаляет отправленные уведомления. События журнала она
только считает; их перенос выполняет администратор ролью миграций по процедуре из `docs/runbook.md`.

**Последствия.** Рабочие выборки не растут бесконечно, а доказательства остаются неизменяемыми. Сроки
хранения заданы значениями по умолчанию и требуют подтверждения юридической службой (вопрос 7), поэтому
задача выключена настройкой `cus.retention.enabled`.

## ADR-0038. PDF карточки собирается PDFBox со встроенным шрифтом DejaVu

**Контекст.** UI-4 требует экспорт карточки в PDF. Базовые шрифты PDF не содержат кириллицы: без
встроенного шрифта документ вышел бы пустым.

**Решение.** Добавлены `org.apache.pdfbox:pdfbox` (Apache 2.0) и шрифты DejaVu Sans в ресурсах
(лицензия Bitstream Vera, свободное распространение, файл `fonts/LICENSE-DejaVu.txt`). Документ собирается
кодом, без HTML-конвертеров.

**Последствия.** Артефакт вырос примерно на 1,5 МБ. Контакты в PDF маскируются по той же политике, что и на
экране, а факт выгрузки попадает в журнал доступа к ПДн: файл не должен становиться способом обойти роль.

## ADR-0037. Шифрование контактов включается флагом, поиск переводится на HMAC

**Контекст.** NFR-3 предусматривает шифрование контактов AES-256-GCM с ключом из окружения и поиском по
HMAC нормализованного значения. Случайный вектор инициализации делает шифртекст разным при каждом
сохранении, поэтому искать по нему нельзя.

**Решение.** Значение и его нормализованная форма шифруются JPA-конвертером, рядом хранится
`subject_contact.search_hmac` — HMAC-SHA256 нормализованного значения на ключе, выведенном из основного.
Поиск выбирает колонку в зависимости от флага. Включение на заполненной базе и ротация ключа выполняются
одной операцией `POST /api/v1/maintenance/contacts/reencrypt`.

**Последствия.** При включённом шифровании база без ключа бесполезна — это записано в runbook рядом с
процедурой резервного копирования. Расшифровка выполняется всегда, независимо от флага: после его
выключения в базе остаются зашифрованные записи, и читать их нужно по-прежнему.

## ADR-0036. Ассеты интерфейса поставляются WebJars, HtmlUnit — тестовая зависимость

**Контекст.** UI-0.2 требует Bootstrap, Bootstrap Icons и HTMX без CDN, а §16.5 — браузерную проверку
сценария отзыва. §14.8 разрешает новые зависимости только с ADR и проверкой лицензии.

**Решение.** Добавлены `org.webjars:bootstrap` (MIT), `org.webjars.npm:bootstrap-icons` (MIT),
`org.webjars.npm:htmx.org` (BSD-2-Clause), `org.webjars:webjars-locator-lite` (MIT),
`thymeleaf-extras-springsecurity6` (Apache 2.0) и тестовый `org.htmlunit:htmlunit` (Apache 2.0).

**Последствия.** Интерфейс работает в закрытом контуре без доступа в интернет; обновление версии ассета —
правка одного свойства в `pom.xml`. Размер артефакта вырос примерно на 2 МБ.

## ADR-0035. Страница самообслуживания живёт на одноразовой ссылке в базе, а не на JWT в адресе

**Контекст.** UI-18 требует встраивания в личный кабинет по ссылке, действующей пять минут, и сессии
страницы на пятнадцать минут. Токен в адресе попадает в историю браузера и логи прокси.

**Решение.** `POST /api/v1/self/ui-sessions` выдаёт одноразовый токен; в базе хранится только его хеш
(таблица `self_ui_session`). При открытии ссылка гасится, адрес страницы остаётся без токена, дальше
работает обычная сессия браузера с ограниченным сроком.

**Последствия.** Ссылку нельзя переиспользовать и нельзя восстановить из таблицы. Хранение в базе, а не в
памяти, позволяет выдать ссылку на одном экземпляре, а открыть на другом.

## ADR-0034. Интерфейс работает на сессии, API остаётся на JWT

**Контекст.** UI-0.3 требует form login с серверной сессией и CSRF, §9 — stateless API на JWT. Одна
цепочка Spring Security не может одновременно отправлять браузер на страницу входа и отвечать машинному
клиенту ProblemDetail.

**Решение.** Две цепочки: `/api/**`, `/actuator/**` и Swagger — stateless JWT; `/ui/**`, `/self/ui/**` и
ассеты — сессия, CSRF и переход на `/ui/login`. Справочник пользователей и ролей общий.

**Последствия.** Токен не нужен в браузере и не попадает в JavaScript. Роль INTEGRATION в интерфейс не
пускается: у неё нет рабочего места, только токен.

## ADR-0033. Сборка карточки клиента вынесена в application-сервис

**Контекст.** Карточку отдаёт и REST (`/subjects/{id}/card`), и экран UI-4. Сборка жила в REST-контроллере,
а §5 запрещает модулю `ui` обращаться к чужому слою `api`.

**Решение.** Появился `registry.application.SubjectCardService`: он считает каналы, согласия и передачи, а
контроллер и интерфейс только раскладывают результат по своему формату.

**Последствия.** Ответ «можно / нельзя» гарантированно один и тот же в API и на экране (FR-6.3). Тот же
приём применён к журналам аудита (`AuditQueryService`).

## ADR-0032. Проверка целостности стала асинхронной, ответ содержит идентификатор запуска

**Контекст.** ADR-0018 фиксировал синхронную реализацию FR-10.4 до этапа 7. Экран UI-15 требует историю
проверок, а на объёмах NFR-1 полный пересчёт цепочек не укладывается в таймаут HTTP.

**Решение.** `POST /api/v1/audit/verify` ставит проверку в очередь и возвращает `id` и статус; результат
читается через `GET /api/v1/audit/verify/{jobId}` (путь из §9), история запусков — через
`GET /api/v1/audit/verify`.
Запуски хранятся в таблице `audit_verification`.

**Последствия.** Контракт эндпоинта изменился: вместо отчёта возвращается запись о запуске. Изменение
опубликовано в `docs/openapi.yaml`, `scripts/demo.sh` переведён на новую форму; потребителей, кроме
демо-сценария, у эндпоинта не было.

## ADR-0031. Почта не участвует в проверке готовности приложения

**Контекст.** `spring-boot-starter-mail` добавляет health-индикатор, который при старте пингует SMTP.
С недоступным почтовым сервером `/actuator/health` отвечает 503, и оркестратор перезапускает исправный
экземпляр, хотя регистрация, проверка каналов и отзыв работают.

**Решение.** `management.health.mail.enabled: false`. Недоставленные письма видны в журнале уведомлений
(`GET /api/v1/notifications`) и в метриках, а не через liveness-проверку.

**Последствия.** Сбой почты не выводит установку из ротации, но и не замечается автоматикой платформы:
мониторинг должен смотреть на долю уведомлений в статусе «не отправлено».

## ADR-0030. Внеочередной запуск задачи уведомлений вынесен в API

**Контекст.** §9 перечисляет только тестовые отправки (FR-9.5). Если планировщик простоял сутки (сбой,
регламентные работы), пороги «ровно N дней» уже пройдены, и без ручного запуска уведомления по ним не
уйдут никогда.

**Решение.** Добавлен `POST /api/v1/notifications/run` для роли ADMIN. Повторные письма исключены той же
дедупликацией по `dedupe_key`, что и у планового прогона.

**Последствия.** Отклонение от списка эндпоинтов §9 — эндпоинт добавлен, а не изменён; контракт
опубликован в `docs/openapi.yaml`. Пропуск порога перестаёт быть безвозвратным.

## ADR-0029. Тело события хранится в outbox готовым, а не собирается при отправке

**Контекст.** Повтор доставки обязан отправить ровно тот же JSON: подпись считается от тела, а потребитель
дедуплицирует по `deliveryId`. Если тело собирать при каждой попытке, оно изменится вместе со справочниками
и настройками.

**Решение.** JSON формируется один раз, в транзакции публикации события, и хранится в `outbox_event.payload`.
Идентификатор записи outbox и есть `deliveryId`, он же уходит в заголовке `X-InConsensu-Delivery-Id`.

**Последствия.** Тело события — снимок на момент изменения данных, а не текущее состояние; это и требуется
доказательству. Изменение формата события затрагивает только новые записи.

## ADR-0028. Уведомление о недоставленном событии не считается ПДн-каналом

**Контекст.** FR-9.3 требует уведомлять ADMIN об исчерпании расписания повторов. Письмо об инциденте
уходит на корпоративные адреса и не должно превращаться в утечку.

**Решение.** В письме только тип события, идентификатор доставки, число попыток и код ошибки транспорта.
Тело события в письмо не попадает; посмотреть его можно в журнале, под аутентификацией и с записью в
`pdn_access_log`.

**Последствия.** Администратор не восстановит содержимое события из письма — придётся открыть In consensu; это
осознанный размен в пользу NFR-3.

## ADR-0027. Дедупликация уведомлений включает получателя, а не только правило и порог

**Контекст.** FR-9.1 задаёт `dedupe_key = правило + согласие + порог`, но у правила бывает несколько
адресатов — явные адреса и все пользователи роли. При уникальном индексе по такому ключу второй адресат
не получил бы письма вовсе.

**Решение.** Ключ дополняется адресом получателя: `правило:согласие:порог:получатель`. Смысл требования
сохраняется — одно уведомление на порог для каждого адресата, повторный запуск задачи писем не удваивает.
Событие для webhook получает суффикс `:webhook` и записывается сразу отправленным: доставку ведёт outbox
со своим журналом.

**Последствия.** Добавление адресата в правило приведёт к письму по уже пройденному порогу — это
ожидаемое поведение, новый адресат ещё ничего не получал.

## ADR-0026. Ограничение частоты самообслуживания — в памяти экземпляра

**Контекст.** FR-8.1 требует rate limit для self-service. Общий счётчик потребовал бы Redis или таблицы с
записью на каждый вызов.

**Решение.** Счётчик в памяти экземпляра: 30 обращений в минуту на клиента.

**Последствия.** Защищает от перебора и от случайного цикла в личном кабинете. При нескольких экземплярах
фактический предел умножается на их число — для кластерного лимита нужен общий счётчик; вынесено в
`OPEN_QUESTIONS.md` (вопрос 17).

## ADR-0023. Зависимость между модулями инвертируется портом на стороне потребителя

**Контекст.** Карточке клиента (`registry`) нужны разрешённые каналы и передачи, а расчёту каналов
(`channels`) и передач (`thirdparty`) нужны согласия из `registry`. Прямые вызовы в обе стороны замыкают
модули в цикл, запрещённый §5, — ArchUnit это и поймал.

**Решение.** Интерфейс объявляется в модуле-потребителе правила (`channels.domain.SubjectConsentPort`,
`thirdparty.domain.SubjectTransferPort`, `thirdparty.domain.PartnerExportDataPort`), а реализуется в
модуле-владельце данных (`registry.application`). Карточка вызывает доменные правила соседних модулей
напрямую — правило чистое и не тянет за собой их инфраструктуру.

**Последствия.** Граф зависимостей остаётся ациклическим, правила §7.6 и §7.7 проверяются юнит-тестами без
базы, а фильтрация категорий ПДн для выгрузки выполняется на стороне `registry` — наружу не выходит ни
одного значения, которое партнёру передавать нельзя (NFR-3). Цена — три интерфейса и по одной реализации
на каждый: без них модули пришлось бы слить.

## ADR-0024. Общие DTO каналов и передач вынесены в `common.api`

**Контекст.** Одну и ту же форму ответа отдают и карточка клиента (`registry`), и отдельные эндпоинты
каналов и передач. Видеть DTO друг друга модулям нельзя (§5), а дублировать контракт нельзя клиенту.

**Решение.** `ChannelView` и `TransferView` живут в `common.api`; отображение доменного решения в них
выполняет слой `api` каждого модуля. Мэппер не может жить в домене: домен не зависит от представления.

**Последствия.** Контракт для клиента один, граница модулей цела. Небольшое повторение кода отображения в
двух контроллерах принято сознательно.

## ADR-0021. Пункты формы сохраняются вместе с черновиком, а не отдельными эндпоинтами

**Контекст.** §9 перечисляет `POST/PUT/DELETE /forms/{id}/items[/{itemId}]`. При этом конструктор UI-8 —
двухколоночный экран с явной кнопкой «Сохранить черновик» (UI-0.9 запрещает автосохранение), то есть
сохраняет форму целиком, включая порядок пунктов.

**Решение.** `PUT /api/v1/forms/{id}` принимает черновик вместе со списком пунктов и заменяет их целиком;
порядок пунктов задаётся позицией в массиве. Отдельных эндпоинтов на пункт нет.

**Последствия.** Одна операция вместо трёх, невозможно рассогласовать порядок пунктов и их состав, и не
нужен отдельный механизм перестановки. Обратная сторона — клиент обязан присылать полный список пунктов;
частичное обновление одного пункта не поддерживается. Отклонение от §9 требует согласования с заказчиком:
записано в `OPEN_QUESTIONS.md` (вопрос 16).

## ADR-0022. Одобрения считаются в пределах одного круга согласования

**Контекст.** FR-2.1 допускает возврат формы на доработку и повторную отправку, FR-2.2 требует сохранять
историю решений целиком. Если засчитывать все одобрения подряд, форма после доработки публиковалась бы с
одобрениями, выданными на старую редакцию текста.

**Решение.** В `consent_form` добавлен столбец `submitted_at`; засчитываются только решения, принятые не
раньше последней отправки на согласование. Прошлые решения остаются в `form_approval` и видны в истории.

**Последствия.** Каждая доработка требует нового круга одобрений от всех обязательных ролей — то есть
согласующие видят именно ту редакцию, которую визируют. Столбца нет в перечне §6, что зафиксировано здесь.

## ADR-0020. Демо-скрипт растёт вместе с этапами

**Контекст.** §13 требует, чтобы `scripts/demo.sh` проходил «для уже реализованных шагов».

**Решение.** Скрипт с самого начала описывает весь сквозной сценарий §11, но нереализованные шаги
печатает как пропущенные с указанием этапа.

**Последствия.** Скрипт всегда зелёный на текущем объёме и одновременно служит наглядным чек-листом
оставшейся работы.
